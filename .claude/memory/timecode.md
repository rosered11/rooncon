**กฎใหม่ (ตัดสินใจแล้ว 2026-08-09):** ใส่ snap zoom แบบ**จังหวะ (rhythm) เป็นเกณฑ์หลัก ไม่ผูกกับความยาวช็อต**

- ความถี่นี้ที่ความยาวคลิปทั่วไป (~500 วิ, ช็อตเฉลี่ย 2.4–2.6 วิหลังเร่งความเร็ว) จะได้ซูมประมาณ **ทุก 20–25 วินาที** — ผู้ใช้ยืนยันว่าความถี่นี้ "ไม่บ่อยจนปวดตา"
- เอฟเฟกต์ซูมยังใช้ค่าเดิม: `1.00 → 1.18` snap ที่ตำแหน่ง ~52% ของช็อตนั้น (ดู schema จริงที่หัวข้อ "Ken Burns เก็บใน `segment.common_keyframes`" ด้านล่าง)
- ช็อตที่ยาวเกิน 3.5 วิเองอยู่แล้ว (คลิปอื่นที่ช็อตยาวกว่านี้) ยังใส่ซูมได้ตามเดิมด้วย ไม่ต้องกันออกจากการนับจังหวะ — สองเงื่อนไขไม่ขัดกัน แค่จังหวะเป็นตัวเสริมให้คลิปช็อตสั้นก็ยังมีซูมบ้าง

## CapCut

CapCut 9 อ่าน `Timelines/<uuid>/draft_info.json` เป็นตัวจริง ไฟล์ `draft_info.json` ที่ราก draft เป็นของเก่าที่ถูกละเลย

## บทเรียน: ห้ามแก้ไฟล์ draft ขณะ CapCut เปิดโปรเจกต์นั้นค้างอยู่

แก้ `draft_info.json` ตรง ๆ ด้วยสคริปต์ตอนที่ CapCut เปิดโปรเจกต์นั้นอยู่ (เห็นใน `ps aux` ว่า process ยังรัน) — พอโปรแกรม autosave มันเขียนทับไฟล์ด้วยข้อมูลในหน่วยความจำของมันเอง (ที่ไม่มีการแก้ไขที่เพิ่งทำ) ทับทุกอย่างที่เพิ่งเขียนไปจนหายสนิท เจอกับ track BGM ที่เพิ่งเพิ่มหายไปทั้ง track
**กฎจากนี้ไป:** ก่อนแก้ `draft_info.json` ด้วยสคริปต์ทุกครั้ง **ต้องให้ผู้ใช้ปิด CapCut ให้สนิทก่อน** (เช็คด้วย `ps aux | grep -i capcut` ว่าไม่มี process เหลือ) ห้ามเปิดแอปอีกจนกว่าจะยืนยันว่าแก้เสร็จแล้ว

## บทเรียน: ใช้ pythainlp ตัดคำช่วยแบ่งช็อตไม่ให้ขาดกลางคำ

แบ่งช็อตด้วยจำนวนตัวอักษรล้วน ๆ (แม้จะยึดเวลาแบบ anchor ถูกแล้ว) ยังเสี่ยงตัดกลางคำผสม เช่น "หลับ" โดนตัดเป็น "หลั" + "บ"
วิธีแก้: ใช้ `pythainlp.tokenize.word_tokenize` (engine `newmm`) ตัดเฉพาะประโยค/วลีที่ยาวเกิน MAXTOK (~30 ตัวอักษร) ก่อนค่อยจัดกลุ่มเป็นช็อต ทำให้จุดตัดตกที่ขอบคำเสมอ

**ต้องรวมเลขที่สะกดเป็นคำ (ปี ค.ศ., เปอร์เซ็นต์) เป็นก้อนเดียวก่อนตัด** ไม่งั้น tokenizer จะตัด "หนึ่งพันเก้าร้อยหกสิบหก" ออกเป็น 6 ชิ้นแยกกัน ทำให้ปี 1966 ไปอยู่คนละช็อตกับตัวเลขท่อนหลัง — merge token ที่เป็นคำจำนวนไทยติดกันให้เป็นก้อนเดียวก่อนแบ่งช็อต

**วันที่:** 2026-08-08

## บทเรียน: ตัดซับ (.srt) ต้อง snap ไปจุดช่องว่างจริง ห้ามใช้ตำแหน่งตัวอักษรดิบ

ถ้าคำนวณจุดตัดบรรทัดซับจากตำแหน่งตัวอักษรที่ interpolate มาตรง ๆ (ไม่ปัดไปจุดช่องว่างของคำ) จะได้ซับขาดกลางคำ เช่น "ทั้งที่" โดนตัดเป็น "ท" กับ "ั้งที่"
ต้องสร้างชุดตำแหน่ง "ขอบคำจริง" จากช่องว่างในสคริปต์ต้นฉบับไว้ก่อน แล้ว snap จุดตัดทุกจุดไปตำแหน่งขอบคำที่ใกล้ที่สุดเสมอ — ตรวจสอบท้ายสุดด้วยการต่อข้อความซับทั้งหมดกลับมาเทียบกับสคริปต์เต็ม ต้องได้ตัวอักษรตรงกัน 100%

## บทเรียน: naive "find(w, last)" ทำ anchor หาย 90%+ เมื่อบทมีตัวเลขสะกดต่างจาก ASR เยอะ

คลิป 003 (คอยีราฟ) สคริปต์สะกดตัวเลขเป็นคำไทยเสมอ ("เจ็ดชิ้น", "สองร้อยล้านปี") แต่ SRT จาก ASR เขียนเป็นเลขอารบิก ("7 ชิ้น", "200 ล้านปี") — วิธี `srt_ns.find(w, last)` แบบ window 12 ตัวอักษรใน skill ได้ anchor แค่ **72 จุด** จากที่ควรได้หลักร้อย เพราะตัวเลขที่สะกดต่างกันทำให้ไม่มี substring ตรงกันเป๊ะยาว 12 ตัวอักษรในช่วงนั้นเลย

**ทางแก้ที่ได้ผล (94%+ ของสคริปต์จับคู่ได้):**
1. **normalize ตัวเลข**: scan SRT หาเลขอารบิก แปลงเป็นคำไทยด้วย `pythainlp.util.num_to_thaiword(n)` ก่อนจับคู่ (ยังคง track ตำแหน่งเดิมใน SRT ไว้คู่กันเพื่อคำนวณเวลา)
2. **ใช้ diff-match-patch หรือ difflib.SequenceMatcher แทน naive find** — ได้ matching blocks ที่ไม่หลุดหายเวลาข้อความมี insert/delete เล็ก ๆ (ASR เพิ่ม/ลดคำ) ทั้งสองไลบรารีให้ผลเหมือนกันในเคสนี้ (94.3% matched)
3. **จุดพลาดที่ทำให้เสียเวลาไปมาก:** สร้าง anchor point แค่ที่ "จุดเริ่ม-จุดจบของแต่ละ matched block" (2 จุดต่อ block) — พอ block ยาว (500+ ตัวอักษร ครอบคลุมหลาย SRT segment) จะกลายเป็น linear interpolation ข้ามช่วงเวลายาวเหมือนวิธีสัดส่วนที่ห้ามใช้ **ต้องเพิ่ม anchor point ที่ทุกจุดที่ตำแหน่งใน SRT ข้าม segment boundary ภายใน block เดียวกันด้วย** ไม่ใช่แค่หัวท้าย block — แก้แล้วได้ 380 anchor points, gap สูงสุดเหลือ 72 ตัวอักษร (~5 วิ) จากเดิม 525 ตัวอักษร (~40 วิ)

**ตรวจสอบว่าแม่นจริง:** สุ่มชื่อเฉพาะ 5 จุด (ชื่อนักวิจัย, ตัวเลขจุดพลิก) เทียบตำแหน่งคำจริงใน SRT (ไม่ใช่จุดเริ่ม segment) ได้คลาด 0.00–0.02 วินาทีทุกจุด — **ระวังอย่าเทียบกับเวลาเริ่มของทั้ง SRT segment เพราะคำที่ต้องการอาจอยู่กลาง/ท้าย segment ทำให้ดูเหมือนคลาดเยอะทั้งที่จริงแม่น**

## บทเรียน: pythainlp tokenizer สับคำเฉพาะ/ชื่อคนที่ไม่อยู่ในดิกชันนารีจนขาดกลางคำ

`word_tokenize(engine='newmm')` เจอชื่อคนที่ทับศัพท์ (เช่น "ฟรีตสัน กาลิส", "แมทธิว วีเดล") จะตัดเป็นพยางค์มั่ว ๆ เช่น `['ฟรี','ต','สัน']` และ `['กา','ลิ','ส']` — ถ้าเอาจุดตัดพวกนี้ไปแบ่งช็อต/ซับ จะได้ภาพหรือซับที่ตัดกลางชื่อคน (เช่น "...ชื่อฟรี" / "ตสัน กาลิส...")

**ทางแก้:** เก็บรายชื่อเฉพาะ/คำทับศัพท์ที่ปรากฏในสคริปต์ไว้ก่อน (ชื่อคน, ศัพท์เทคนิคทับศัพท์อย่าง "เมแทบอลิซึม") แล้วสร้าง custom dict ผ่าน `pythainlp.tokenize.Tokenizer(custom_dict=set(thai_words()) | {'ฟรีตสัน','กาลิส','แมทธิว','วีเดล','เมแทบอลิซึม', ...}, engine='newmm')` — ต้องเช็คทุกครั้งที่ขึ้นคลิปใหม่ว่ามีชื่อเฉพาะ/ศัพท์ทับศัพท์อะไรบ้างในสคริปต์ แล้วเพิ่มเข้า custom dict ก่อน tokenize เสมอ ไม่ใช่เชื่อ dictionary เริ่มต้นเฉย ๆ

**วิธีเช็คว่ายังมีคำหลุดเหลือ:** หลัง tokenize ให้กรอง token สั้น (≤3 ตัวอักษร) ที่ไม่ใช่คำไทยทั่วไป (กรองด้วย set คำสั้นที่พบบ่อยไว้) มาดูด้วยตาว่าเป็นเศษพยางค์ของคำอะไรหรือเปล่า

**วันที่:** 2026-08-09

## บทเรียน: schema `extra_material_refs` ของ CapCut — ลำดับหมวดหมู่ตายตัวต่อ track type

จากงานเพิ่ม end credit ใน `003_giraffe_neck` เรียนรู้ว่า `extra_material_refs` ของแต่ละ segment คือ list ของ id ที่ชี้ไปยัง "material ปลีกย่อย" หลายหมวดใน `materials.*` (ค่า default/placeholder เกือบทั้งหมด ไม่มีเนื้อหาจริง) — **แต่ละ segment ต้องมีชุดของตัวเองแยกกัน ห้ามใช้ id ซ้ำข้าม segment** แม้ค่าข้างในจะเหมือนกันทุกตัวก็ตาม (โคลนแล้วสุ่ม id ใหม่เสมอ)

ลำดับหมวดที่เจอจริง (คงที่ตาม track type):

- **video segment** (8 refs): `speeds → placeholder_infos → canvases → material_animations → sound_channel_mappings → material_colors → loudnesses → vocal_separations`
- **audio segment** (6 refs, ทั้งเสียงพากย์และ BGM): `speeds → placeholder_infos → beats → sound_channel_mappings → loudnesses → vocal_separations`

วิธีปลอดภัยสุด: อย่าจำลำดับตายตัว ให้เขียนสคริปต์ที่ไล่หาหมวดหมู่จริงของแต่ละ ref id จาก segment ตัวอย่าง (loop ทุก key ใน `materials` ที่เป็น list แล้วเทียบ `id`) แล้วโคลนตามหมวดที่เจอจริงเสมอ ไม่ต้อง hardcode

## บทเรียน: ไม่มี `audio_fades` ใน JSON ของ track BGM — fade in/out ถูก bake เข้าไฟล์ wav เลย

## บทเรียน: แก้ speed เฉพาะ segment เดียว (ไม่แตะ track อื่น) ต้องเช็คว่า speed material ถูกใช้ร่วมกับ segment อื่นหรือไม่ก่อนแก้

เคสจริง: ทดสอบเปลี่ยนเสียงพากย์ของ `003_giraffe_neck` จาก `speed=1.1` กลับเป็น `1.0` ชั่วคราวเพื่อฟังเทียบว่าเสียงแตก/เพี้ยนมาจากอัลกอริทึมเร่งความเร็วของ CapCut หรือไม่ — งานแบบนี้ต้องแก้ **แค่ segment เดียว** โดยไม่กระทบ segment อื่นที่อาจ share material เดียวกัน

**วิธีระบุ material ที่ปลอดภัยจะแก้ (ไม่ใช่เดา):**
1. หา segment เป้าหมายจาก `material_id` ที่ชี้ไปไฟล์เสียงจริง (เช่น `ElevenLabs_003_mastered.wav`) ผ่าน `.tracks[].segments[] | select(.material_id==...)`
2. ในบรรดา `extra_material_refs` ของ segment นั้น หาตัวที่อยู่ใน `materials.speeds[]` โดยกรองด้วยค่า `speed` ที่ตรงกับ `segment.speed` ปัจจุบัน (เช่น `speed==1.1`) แทนการเดา index/ตำแหน่งในลิสต์ — `materials.speeds[]` มีหลายสิบรายการ ส่วนใหญ่เป็น `speed:1.0` (default ของ segment ภาพ) มีแค่ตัวเดียวที่ตรงกับ 1.1 พอดีในเคสนี้
3. **ก่อนแก้ ต้องเช็คว่า speed material id นั้นถูกอ้างโดย segment อื่นด้วยหรือไม่**: `jq --arg id "<speed_material_id>" '[.tracks[].segments[] | select(.extra_material_refs[]? == $id)]'` — ถ้าเจอมากกว่า 1 segment ห้ามแก้ material ร่วมตรง ๆ (จะกระทบ segment อื่นโดยไม่ตั้งใจ) ต้อง clone material ใหม่แยกให้ segment เป้าหมายอ้างอิงเอง แล้วค่อยแก้ตัวโคลน — เคสนี้เช็คแล้วพบว่า material ผูกกับ segment เดียว (1:1) จึงแก้ตรงได้เลยโดยปลอดภัย
4. เปลี่ยน `segment.speed` ให้ตรงกับ material ที่แก้ไปด้วยเสมอ (สอง field ต้องซิงค์กัน — CapCut เก็บ speed ซ้ำสองที่: ใน segment เองและใน material speeds ที่ extra_material_refs ชี้ไป)
5. เมื่อ speed=1.0 ความยาว `target_timerange.duration` ต้องเท่ากับ `source_timerange.duration` เต็มไฟล์เสมอ (ไม่มีการเร่ง/ผ่อนความเร็วแล้ว)
6. ตรวจสอบผลด้วย `diff <(jq -S . ก่อนแก้) <(jq -S . หลังแก้)` ต้องเห็นแค่บรรทัดที่ตั้งใจแก้เท่านั้น (เคสนี้คือ 3 บรรทัดเป๊ะ: speed ในสอง object + target duration 1 ค่า) เป็นวิธี sanity check ที่แม่นกว่าการอ่านด้วยตา

**หมายเหตุ:** top-level `duration` ของ project (`data["duration"]` ที่ root ของ draft_info.json) **ไม่ได้ปรับตามความยาว track เสียงที่ยาวขึ้นอัตโนมัติ** — เคสทดสอบนี้ตั้งใจปล่อยไว้ตามเดิม (502.42s) ในขณะที่เสียงพากย์ยาวจริง 552.63s เพราะเป็นการทดสอบฟังเสียงชั่วคราว ไม่ใช่ค่าสุดท้าย — **ยังไม่ยืนยันว่า CapCut จะเล่นเสียงเกินขอบ project duration เดิมได้เต็มหรือไม่ ต้องรอดูตอนเปิดแอปจริง** ถ้าจะใช้ค่านี้เป็นค่าจริงถาวร (ไม่ใช่แค่ทดสอบ) ต้องอัปเดต top-level `duration` ให้ตรงกับ track ที่ยาวที่สุดด้วย

## บทเรียน: เสียงแตกจาก CapCut speed engine เรียลไทม์ — แก้ถาวรด้วยการเร่งไฟล์นอก CapCut แล้ว import แทน speed field

คลิป 003 (giraffe-neck) เจอเสียงแตกตอนตั้ง `segment.speed = 1.1` ให้ CapCut เร่งความเร็วเสียงพากย์เรียลไทม์เอง — ทดสอบ `speed = 1.0` แล้วเสียงสะอาด ยืนยันว่าเสียงแตกมาจาก speed engine ของ CapCut เอง ไม่ใช่ปัญหาไฟล์ต้นทาง

**ทางแก้ถาวร:** เร่งความเร็วไฟล์เสียงพากย์มาสเตอร์แล้วด้วย `ffmpeg atempo=1.1` นอก CapCut ก่อน (ได้ไฟล์ `*_110x.wav`) แล้ว import เป็น material ใหม่ ตั้ง `segment.speed = 1.0` (ไม่เร่งซ้ำ) — `source_timerange.duration` และ `target_timerange.duration` ของ segment ต้องเท่ากับความยาวไฟล์ 110x จริง (วัดด้วย `wave` module ไม่ใช่ ffprobe ตามบทเรียนเดิม)

**ขั้นตอนแก้ segment เสียงพากย์ให้ชี้ไฟล์ใหม่ (ยืนยันวิธีที่ปลอดภัย):**
1. หา segment id เดิม + material_id เดิมที่ segment ชี้ไป
2. เช็คว่า material นั้น (และ speed material ใน `extra_material_refs`) ถูกใช้กับ segment เดียวนี้เท่านั้น (นับจำนวน segment ที่อ้างถึงแต่ละ id) ก่อนแก้ กันกระทบ segment อื่นที่ share material เดียวกันโดยไม่รู้ตัว
3. **โคลน material entry เดิมเป็นก้อนใหม่** (deep copy) เปลี่ยนแค่ `id` (uuid4 ใหม่), `unique_id`, `local_material_id`, `music_id`, `name`, `path`, `duration` — อย่าแก้ path ของ material เดิมตรง ๆ เพราะจะเสียของเดิมไว้ทดสอบย้อนกลับไม่ได้ถ้าจำเป็น
4. แก้ segment: `material_id` ชี้ไป material ใหม่, `speed` เป็น 1.0, `source_timerange.duration` และ `target_timerange.duration` เท่ากับ duration ของไฟล์ใหม่จริง
5. Speed material ใน `extra_material_refs` ตั้ง `speed: 1.0` (ถ้าเดิมเป็น 1.0 อยู่แล้วจากการทดสอบรอบก่อนไม่ต้องแตะ)

**วิธีตรวจสอบว่าแก้แค่จุดที่ตั้งใจ:** เทียบ segment id list ของทุก track ระหว่างไฟล์ก่อน/หลังแก้ (ต้อง identical ทั้ง type/count/order) แล้วไล่ diff เนื้อหา segment ทีละตัวด้วย id เดียวกัน — ถ้ามี segment อื่นเปลี่ยนไปโดยไม่ตั้งใจจะเห็นทันที (ในเคสนี้ยืนยันว่าเปลี่ยนแค่ segment เสียงพากย์ 1 ตัวจากทั้งหมด 218 segment ในโปรเจกต์)

**บั๊กที่ต้องระวังตอนเขียนสคริปต์ query ตรวจสอบ (ไม่ใช่บั๊กในไฟล์ draft):** เขียน loop ซ้อน `for track in tracks: if track['type']=='audio': for seg in track['segments']: if seg matches...` แล้วใช้ตัวแปร `seg` ต่อนอกลูปเพื่ออ้างอิง — ตัวแปรจะถูก overwrite เป็น segment ตัวสุดท้ายที่ loop ผ่าน (อาจเป็นคนละ track ที่ type ตรงกันแต่ id ไม่ตรง) ไม่ใช่ตัวที่ match เงื่อนไข ทำให้ debug หลงประเด็นไปเช็ค material ผิดตัว (เจอตอนเช็คว่า voice segment ชี้ไปไฟล์ไหน ดันไปได้ข้อมูล bgm.wav แทน) — **ต้องเก็บผลลัพธ์ที่ match เงื่อนไขไว้ในตัวแปรแยกต่างหาก (เช่น `voice_seg = seg` เฉพาะตอน if เข้าเงื่อนไข) ไม่ใช้ตัวแปร loop เดิมอ้างอิงต่อนอกลูป**

## pythainlp custom_dict blacklist (สะสม — ลบออกจาก `thai_words()` ก่อน tokenize ทุกคลิป)

`thai_words()` มีเศษพยางค์ที่ดันเป็น "คำจริง" ในดิกชันนารี ทำให้ newmm เลือกเส้นทางตัดคำผิด (เช่น "ทุก" → "ทุ"+"ก" เพราะ "ทุ" มีอยู่จริงใน dict) — ต้องลบออกก่อนสร้าง custom dict ทุกครั้ง

**สะสมถึงคลิป 009:** `{'แร', 'ทุ', 'ทด', 'บอ', 'ถู', 'ออ'}`

**วิธีเช็คว่ายังมีคำหลุดเหลือ:** รัน tokenizer เต็มสคริปต์แล้ว list token ที่ยาว ≤2 ตัวอักษรทั้งหมด กรองด้วย whitelist คำสั้นที่รู้จัก (มา/มี/ใน/ก็/ไป/จะ/กฎ/ปี/วน/จน/ไฟ/ดู/ทำ ฯลฯ) ที่เหลือเปิด context 4-5 token รอบ ๆ ดูด้วยตาว่าเป็นเศษพยางค์หรือไม่ เจอคำใหม่ให้เพิ่มเข้า set นี้ทุกคลิป
