### บทเรียน: เกณฑ์ ">3.5 วิ" อย่างเดียวใช้ไม่ได้กับคลิปที่ช็อตสั้น — เปลี่ยนเป็นใส่ตามจังหวะแทน

คลิป 003 ทุกช็อตสั้นกว่า 3.5 วิหมด (ยาวสุด 3.3 วิที่ความเร็วธรรมชาติ, 3.0 วิหลังเร่ง 1.10x) — ผลคือ **ไม่มี Ken Burns เลยทั้งคลิป 213 ช็อต** ทั้งที่กฎเดิมทำตามถูกทุกตัวอักษร (ยืนยันคำนวณด้วยและเปิด `draft_info.json` ดูตรงว่าไม่มี `common_keyframes` ซูมสักช็อตเดียว) — เกณฑ์ duration ล้วนๆ จึงมีช่องโหว่กับคลิปที่ช็อตสั้นเป็นพิเศษ ขัดกับเจตนาเดิมของกฎ (กันคลิปนิ่งเกินไป)

**กฎใหม่ (ตัดสินใจแล้ว 2026-08-09):** ใส่ snap zoom แบบ**จังหวะ (rhythm) เป็นเกณฑ์หลัก ไม่ผูกกับความยาวช็อต**
- เลือกช็อตให้ซูมประมาณ**ทุก 8–12 ช็อต** สุ่มช่วงห่างไม่ตายตัวในกรอบนี้ (กันดูเป็นแพทเทิร์นตายตัวที่เดาจังหวะได้ล่วงหน้า — คนละปัญหากับที่เจอตอนช็อตซ้ำติดกัน แต่หลักการเดียวกันคือห้ามคาดเดาได้)
- ความถี่นี้ที่ความยาวคลิปทั่วไป (~500 วิ, ช็อตเฉลี่ย 2.4–2.6 วิหลังเร่งความเร็ว) จะได้ซูมประมาณ **ทุก 20–25 วินาที** — ผู้ใช้ยืนยันว่าความถี่นี้ "ไม่บ่อยจนปวดตา"
- เอฟเฟกต์ซูมยังใช้ค่าเดิม: `1.00 → 1.18` snap ที่ตำแหน่ง ~52% ของช็อตนั้น (ดู schema จริงที่หัวข้อ "Ken Burns เก็บใน `segment.common_keyframes`" ด้านล่าง)
- ช็อตที่ยาวเกิน 3.5 วิเองอยู่แล้ว (คลิปอื่นที่ช็อตยาวกว่านี้) ยังใส่ซูมได้ตามเดิมด้วย ไม่ต้องกันออกจากการนับจังหวะ — สองเงื่อนไขไม่ขัดกัน แค่จังหวะเป็นตัวเสริมให้คลิปช็อตสั้นก็ยังมีซูมบ้าง

## บทเรียน: ใช้ pythainlp ตัดคำช่วยแบ่งช็อตไม่ให้ขาดกลางคำ

แบ่งช็อตด้วยจำนวนตัวอักษรล้วน ๆ (แม้จะยึดเวลาแบบ anchor ถูกแล้ว) ยังเสี่ยงตัดกลางคำผสม เช่น "หลับ" โดนตัดเป็น "หลั" + "บ"
วิธีแก้: ใช้ `pythainlp.tokenize.word_tokenize` (engine `newmm`) ตัดเฉพาะประโยค/วลีที่ยาวเกิน MAXTOK (~30 ตัวอักษร) ก่อนค่อยจัดกลุ่มเป็นช็อต ทำให้จุดตัดตกที่ขอบคำเสมอ

**ต้องรวมเลขที่สะกดเป็นคำ (ปี ค.ศ., เปอร์เซ็นต์) เป็นก้อนเดียวก่อนตัด** ไม่งั้น tokenizer จะตัด "หนึ่งพันเก้าร้อยหกสิบหก" ออกเป็น 6 ชิ้นแยกกัน ทำให้ปี 1966 ไปอยู่คนละช็อตกับตัวเลขท่อนหลัง — merge token ที่เป็นคำจำนวนไทยติดกันให้เป็นก้อนเดียวก่อนแบ่งช็อต

**วันที่:** 2026-08-08

## บทเรียน: ตัดซับ (.srt) ต้อง snap ไปจุดช่องว่างจริง ห้ามใช้ตำแหน่งตัวอักษรดิบ

ถ้าคำนวณจุดตัดบรรทัดซับจากตำแหน่งตัวอักษรที่ interpolate มาตรง ๆ (ไม่ปัดไปจุดช่องว่างของคำ) จะได้ซับขาดกลางคำ เช่น "ทั้งที่" โดนตัดเป็น "ท" กับ "ั้งที่"
ต้องสร้างชุดตำแหน่ง "ขอบคำจริง" จากช่องว่างในสคริปต์ต้นฉบับไว้ก่อน แล้ว snap จุดตัดทุกจุดไปตำแหน่งขอบคำที่ใกล้ที่สุดเสมอ — ตรวจสอบท้ายสุดด้วยการต่อข้อความซับทั้งหมดกลับมาเทียบกับสคริปต์เต็ม ต้องได้ตัวอักษรตรงกัน 100%

## บทเรียน: naive "find(w, last)" ทำ anchor หาย 90%+ เมื่อบทมีตัวเลขสะกดต่างจาก ASR เยอะ

คลิป 003 (คอยีราฟ) สคริปต์สะกดตัวเลขเป็นคำไทยเสมอ ("เจ็ดชิ้น", "สองร้อยล้านปี") แต่ SRT จาก ASR เขียนเป็นเลขอารบิก ("7 ชิ้น", "200 ล้านปี") — วิธี `srt_ns.find(w, last)` แบบ window 12 ตัวอักษรใน skill ได้ anchor แค่ **72 จุด** จากที่ควรได้หลักร้อย เพราะตัวเลขที่สะกดต่างกันทำให้ไม่มี substring ตรงกันเป๊ะยาว 12 ตัวอักษรในช่วงนั้นเลย

**ทางแก้ที่ได้ผล (94%+ ของสคริปต์จับคู่ได้):**
1. **normalize ตัวเลข**: scan SRT หาเลขอารบิก แปลงเป็นคำไทยด้วย `pythainlp.util.num_to_thaiword(n)` ก่อนจับคู่ (ยังคง track ตำแหน่งเดิมใน SRT ไว้คู่กันเพื่อคำนวณเวลา)
2. **ใช้ diff-match-patch หรือ difflib.SequenceMatcher แทน naive find** — ได้ matching blocks ที่ไม่หลุดหายเวลาข้อความมี insert/delete เล็ก ๆ (ASR เพิ่ม/ลดคำ) ทั้งสองไลบรารีให้ผลเหมือนกันในเคสนี้ (94.3% matched)
3. **จุดพลาดที่ทำให้เสียเวลาไปมาก:** สร้าง anchor point แค่ที่ "จุดเริ่ม-จุดจบของแต่ละ matched block" (2 จุดต่อ block) — พอ block ยาว (500+ ตัวอักษร ครอบคลุมหลาย SRT segment) จะกลายเป็น linear interpolation ข้ามช่วงเวลายาวเหมือนวิธีสัดส่วนที่ห้ามใช้ **ต้องเพิ่ม anchor point ที่ทุกจุดที่ตำแหน่งใน SRT ข้าม segment boundary ภายใน block เดียวกันด้วย** ไม่ใช่แค่หัวท้าย block — แก้แล้วได้ 380 anchor points, gap สูงสุดเหลือ 72 ตัวอักษร (~5 วิ) จากเดิม 525 ตัวอักษร (~40 วิ)

**ตรวจสอบว่าแม่นจริง:** สุ่มชื่อเฉพาะ 5 จุด (ชื่อนักวิจัย, ตัวเลขจุดพลิก) เทียบตำแหน่งคำจริงใน SRT (ไม่ใช่จุดเริ่ม segment) ได้คลาด 0.00–0.02 วินาทีทุกจุด — **ระวังอย่าเทียบกับเวลาเริ่มของทั้ง SRT segment เพราะคำที่ต้องการอาจอยู่กลาง/ท้าย segment ทำให้ดูเหมือนคลาดเยอะทั้งที่จริงแม่น**

## บทเรียน: pythainlp tokenizer สับคำเฉพาะ/ชื่อคนที่ไม่อยู่ในดิกชันนารีจนขาดกลางคำ

`word_tokenize(engine='newmm')` เจอชื่อคนที่ทับศัพท์ (เช่น "ฟรีตสัน กาลิส", "แมทธิว วีเดล") จะตัดเป็นพยางค์มั่ว ๆ เช่น `['ฟรี','ต','สัน']` และ `['กา','ลิ','ส']` — ถ้าเอาจุดตัดพวกนี้ไปแบ่งช็อต/ซับ จะได้ภาพหรือซับที่ตัดกลางชื่อคน (เช่น "...ชื่อฟรี" / "ตสัน กาลิส...")

**ทางแก้:** เก็บรายชื่อเฉพาะ/คำทับศัพท์ที่ปรากฏในสคริปต์ไว้ก่อน (ชื่อคน, ศัพท์เทคนิคทับศัพท์อย่าง "เมแทบอลิซึม") แล้วสร้าง custom dict ผ่าน `pythainlp.tokenize.Tokenizer(custom_dict=set(thai_words()) | {'ฟรีตสัน','กาลิส','แมทธิว','วีเดล','เมแทบอลิซึม', ...}, engine='newmm')` — ต้องเช็คทุกครั้งที่ขึ้นคลิปใหม่ว่ามีชื่อเฉพาะ/ศัพท์ทับศัพท์อะไรบ้างในสคริปต์ แล้วเพิ่มเข้า custom dict ก่อน tokenize เสมอ ไม่ใช่เชื่อ dictionary เริ่มต้นเฉย ๆ

**วิธีเช็คว่ายังมีคำหลุดเหลือ:** หลัง tokenize ให้กรอง token สั้น (≤3 ตัวอักษร) ที่ไม่ใช่คำไทยทั่วไป (กรองด้วย set คำสั้นที่พบบ่อยไว้) มาดูด้วยตาว่าเป็นเศษพยางค์ของคำอะไรหรือเปล่า

`materials.videos[].type == "photo"` มี `duration` เป็นค่า placeholder ใหญ่คงที่ (`10800000000` = 3 ชม.) ไม่ใช่ความยาวจริง ความยาวจริงกำหนดจาก `segment.source_timerange` / `target_timerange` เท่านั้น (สองค่านี้เท่ากันเสมอสำหรับภาพนิ่ง) และ `segment.speed` ของภาพนิ่งคงที่ `1.0` เสมอแม้คลิปทั้งตัวจะ "เร่ง 1.10x" ก็ตาม

**การเร่งความเร็วคลิปทั้งตัว (เช่น 1.10x) ไม่ได้ทำผ่าน field "speed" ของ segment ภาพ** — วิธีจริงคือ **หารเวลา in/out ของทุกช็อต (จาก timecode_map ที่คำนวณไว้ที่ความเร็วธรรมชาติ) ด้วยตัวคูณความเร็วเอง** แล้วค่อยใส่เป็น target_timerange ของแต่ละ segment ภาพ (คำนวณแบบสะสม `target_start_i = target_end_{i-1}` กัน rounding drift สะสมจนเกิดช่องว่าง)

ส่วนไฟล์เสียงพากย์ (WAV จริง มีคลื่นเสียงจริง) ใช้กลไก speed จริงของ CapCut: `segment.speed = 1.1`, `source_timerange.duration` = ความยาวไฟล์ธรรมชาติจริง (นับ frame จาก `wave` module ไม่ใช่ ffprobe เพราะแม่นกว่า), `target_timerange.duration = round(source/1.1)`

ยืนยันรูปแบบนี้จากโปรเจกต์ทดลอง `draft004_110x` ที่มีอยู่ในเครื่อง (ไม่ใช่แม่แบบทางการแต่ช่วยยืนยัน pattern เดียวกัน)

### Ken Burns เก็บใน `segment.common_keyframes` ไม่ใช่ `materials.material_animations`
`materials.material_animations[]` (type `sticker_animation`) ที่ทุก segment อ้างถึงเป็นแค่ placeholder ว่างเปล่า (`animations: []`) เสมอ — **Ken Burns จริงอยู่ใน `segment.common_keyframes`**:
```json
"common_keyframes": [{
  "property_type": "KFTypeScaleX",
  "keyframe_list": [
    {"time_offset": 0, "values": [1.0]},
    {"time_offset": <52% ของ target_timerange.duration>, "values": [1.0]},
    {"time_offset": <52%+100000 (0.1s)>, "values": [1.18]}
  ]
}]
```
มีแค่ `KFTypeScaleX` เท่านั้น ไม่มี `KFTypeScaleY` คู่กัน (แกน Y ตามแกน X เองผ่าน `uniform_scale.on: true` ของ segment) — เกณฑ์ >3.5 วิที่ทีมตั้งไว้ ใช้กับ **target_timerange.duration หลังเร่งความเร็วแล้ว** (ไม่ใช่ความยาวธรรมชาติก่อนเร่ง) เพราะเป็นความยาวที่คนดูเห็นจริงบนไทม์ไลน์ — คลิป 003 รอบแรกไม่มีช็อตไหนถึงเกณฑ์เลยแม้แต่ช็อตเดียว (max หลังเร่งคือ ~3.0 วิ) จึงไม่มี Ken Burns เลยทั้งคลิป **⚠️ อัปเดต 2026-08-09: เปลี่ยนกฎเป็นใส่ตามจังหวะทุก 8–12 ช็อตแทนแล้ว (ดูหัวข้อ "บทเรียน: เกณฑ์ >3.5 วิ อย่างเดียวใช้ไม่ได้กับคลิปที่ช็อตสั้น" ด้านบน) ต้องย้อนไปเติม `common_keyframes` ให้คลิป 003 เพิ่ม**

### segment แต่ละตัว (ภาพ/เสียง) ผูกกับ material ผ่าน `extra_material_refs` 6–8 ตัว เสมอ
ภาพ (8 refs): `speed, placeholder_info, canvas, material_animation, sound_channel_mapping, material_color, loudness, vocal_separation`
เสียง (6 refs): `speed, placeholder_info, beats, sound_channel_mapping, loudness, vocal_separation`
ทุก segment ต้องมีครบชุดแม้ค่าจะเป็น default ว่างเปล่า มิฉะนั้น CapCut อาจ error ตอนเปิด — `loudnesses[].enable` และ `vocal_separations[].choice` ต้องเป็น `false`/`0` เสมอ (คือค่า "ปิด" ที่กฎช่องต้องการอยู่แล้ว)

### BGM สอง segment มาจากไฟล์เดียวกัน ต่อเนื่อง ไม่ loop ซ้อน
`materials.audios` ของ BGM ทั้ง 2 segment (ระหว่างพากย์ 10% / end credit 40%) ชี้ไป **material_id เดียวกัน** ไฟล์เดียวกัน (`bgm.wav` ที่ loop+crossfade+trim มาแล้วนอก CapCut ด้วย ffmpeg ตามสูตรใน `decisions.md`) แค่ตัด `source_timerange.start` ให้ต่อกันพอดี (segment 2 เริ่มที่ `source_timerange.start` = จุดจบของ segment 1) — **fade in/out ของ BGM ไม่ได้ทำผ่าน CapCut (ไม่มี `audio_fades` material ใช้งานเลย, count เป็น 0 เสมอ)** ต้อง bake `afade` เข้าไปในไฟล์ wav ตอนเตรียมด้วย ffmpeg ก่อน import เท่านั้น

### ภาพต้นทาง 1376×768 อัปสเกลเป็น 1920×1080 ด้วย stretch ตรง ๆ ไม่ crop
เทียบ pixel MSE ระหว่างภาพต้นฉบับ resize แบบ stretch ตรงกับภาพ `final_upscaled/` ของ 002 จริง (MSE 0.68) กับแบบ scale-then-center-crop (MSE 92.7) — stretch ตรงคือวิธีที่ใช้จริง แม้ aspect ratio จะต่างกันเล็กน้อย (1376:768 = 1.7917 vs 1920:1080 = 1.7778) ก็ไม่ครอบตัด ใช้ `Image.resize((1920,1080), LANCZOS)` ตรง ๆ ได้เลย

### `draft_meta_info.json` มี `draft_fold_path`/`draft_name` ต้องอัปเดตด้วยตอนโคลนโปรเจกต์
ไฟล์นี้อยู่นอก `Timelines/` ที่รากโปรเจกต์ ใช้เก็บ path เดิมของโปรเจกต์ต้นแบบ (เช่น ยังชี้ไป `002_first_night_sleep` หลังโคลน) ต้องแก้ `draft_name`, `draft_fold_path`, `tm_draft_modified`, `tm_duration` ให้ตรงโปรเจกต์ใหม่ด้วย ไม่งั้น CapCut อาจสับสนเรื่อง path แม้ตัว `draft_info.json` จะถูกต้องแล้วก็ตาม — ไฟล์อื่น ๆ ที่ยังอ้างชื่อโปรเจกต์เดิม (`template.json`, `template-2.tmp`, `mini_draft.json`) ไม่ได้แก้เพราะไม่ใช่ไฟล์ที่ CapCut อ่านเป็นหลัก (อยู่นอกขอบเขตกฎเหล็กของ skill) — ยังไม่ยืนยันว่าจำเป็นต้องแก้ไหม รอดูตอนเปิด CapCut จริงครั้งแรกกับโปรเจกต์ที่โคลนมา
**`root_meta_info.json`** (อยู่นอกโฟลเดอร์โปรเจกต์ ระดับ `com.lveditor.draft/` เป็น index ของ CapCut ทั้งหมด) ยังไม่ถูกแก้เช่นกัน — ไม่แน่ใจว่า CapCut auto-scan โฟลเดอร์ใหม่ตอนเปิดแอปเองหรือไม่ ต้องรอดูผลตอนเปิดจริง ถ้าโปรเจกต์ใหม่ไม่ขึ้นในลิสต์ให้ลองใช้ "Import"/"Open" ชี้ path ตรง ๆ ก่อน แล้วค่อยพิจารณาแก้ root_meta_info.json (ระวังเพราะกระทบทุกโปรเจกต์ในเครื่อง)

## บทเรียน: schema `extra_material_refs` ของ CapCut — ลำดับหมวดหมู่ตายตัวต่อ track type

จากงานเพิ่ม end credit ใน `003_giraffe_neck` เรียนรู้ว่า `extra_material_refs` ของแต่ละ segment คือ list ของ id ที่ชี้ไปยัง "material ปลีกย่อย" หลายหมวดใน `materials.*` (ค่า default/placeholder เกือบทั้งหมด ไม่มีเนื้อหาจริง) — **แต่ละ segment ต้องมีชุดของตัวเองแยกกัน ห้ามใช้ id ซ้ำข้าม segment** แม้ค่าข้างในจะเหมือนกันทุกตัวก็ตาม (โคลนแล้วสุ่ม id ใหม่เสมอ)

ลำดับหมวดที่เจอจริง (คงที่ตาม track type):

- **video segment** (8 refs): `speeds → placeholder_infos → canvases → material_animations → sound_channel_mappings → material_colors → loudnesses → vocal_separations`
- **audio segment** (6 refs, ทั้งเสียงพากย์และ BGM): `speeds → placeholder_infos → beats → sound_channel_mappings → loudnesses → vocal_separations`

วิธีปลอดภัยสุด: อย่าจำลำดับตายตัว ให้เขียนสคริปต์ที่ไล่หาหมวดหมู่จริงของแต่ละ ref id จาก segment ตัวอย่าง (loop ทุก key ใน `materials` ที่เป็น list แล้วเทียบ `id`) แล้วโคลนตามหมวดที่เจอจริงเสมอ ไม่ต้อง hardcode

## บทเรียน: ไม่มี `audio_fades` ใน JSON ของ track BGM — fade in/out ถูก bake เข้าไฟล์ wav เลย

ตรวจ `003_giraffe_neck` แล้วพบว่า BGM segment ไม่มี fade material อ้างอิงใน `extra_material_refs` เลย (ไม่มีหมวด audio_fades ถูกใช้งาน) เพราะ fade in 2 วิ/fade out 3 วิ ถูกทำด้วย ffmpeg (`afade`) ใส่ไว้ในไฟล์ `bgm.wav` เองตั้งแต่ก่อน import เข้า CapCut แล้ว — ไม่ต้องหา/ตั้งค่า fade ผ่าน JSON เลย

## บทเรียน: ต่อ BGM segment สองช่วง volume ต่างกันแบบไม่มีรอยตัด ทำได้ด้วยการแบ่ง segment ไม่ใช่ตัดไฟล์เสียง

เวลาต้องการให้ BGM ไฟล์เดียวกันมีความดังสองระดับ (เช่น 10% ระหว่างมีเสียงพากย์ → 40% ช่วง end credit ไม่มีเสียงพูดแข่ง) โดยไม่ให้มีรอยตัด/เริ่มเพลงใหม่ ให้:
1. เรนเดอร์ไฟล์เสียง BGM ยาวคลุมทั้งความยาว timeline สุดท้าย (main content + end credit) เป็นไฟล์เดียวต่อเนื่อง (ใช้เทคนิค loop+crossfade เดิม แต่ trim ยาวขึ้น และย้ายจุด fade out ไปไว้ที่ปลายไฟล์จริงแทน)
2. ใน `draft_info.json` สร้าง audio segment ใหม่อีกอันที่ชี้ `material_id` **เดียวกัน** กับ segment เดิม แต่ `source_timerange.start` ต่อจากจุดที่ segment แรกจบพอดี แล้วตั้ง `volume` ต่างกันได้อิสระต่อ segment
3. ผลคือเสียงเล่นต่อเนื่องไม่มีช่องว่าง/ไม่มีรอยตัดที่ได้ยิน แต่ความดังเปลี่ยนขั้นบันไดตรงจุดต่อ segment
