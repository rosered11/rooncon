## เตรียมเสียงตัวอย่างสำหรับ train voice clone — ต่างจาก mastering เสียงพากย์ปกติ

โจทย์ "เอาไฟล์เสียงที่อัดเองไปเทรนเป็นเสียงพากย์" (เช่นฟีเจอร์ voice cloning ของ ElevenLabs) มีเป้าหมายคนละแบบกับ mastering เสียงพากย์ไปลง YouTube — **ห้ามใช้เชนเดียวกัน**:

| | mastering เสียงพากย์ (YouTube) | เสียงตัวอย่าง train voice clone |
|---|---|---|
| เป้า LUFS | ‑14 ถึง ‑16 (ดังเต็มมาตรฐานแพลตฟอร์ม) | **‑20 LUFS** พอ — ไฟล์นี้ไม่ได้เผยแพร่ตรง ๆ ต้องการ headroom ธรรมชาติมากกว่า |
| Dynamics | บีบด้วย limiter หนัก ท้ายเชนเสมอ | compressor **เบา ๆ** เท่านั้น (~2.3:1) กัน "ความรู้สึก"/อารมณ์เสียงหายไป ห้ามบีบจนแบน |
| ช่วงเงียบ | ตัด mid-roll เท่านั้น ไม่แตะช่วงหยุดพูด | **ต้องหดช่วงเงียบทุกจุดเพื่อคุมความยาว/ขนาดไฟล์** โดยไม่ตัดคำพูดทิ้งแม้แต่คำเดียว |

**วิธีหดช่วงเงียบแบบไม่ตัดคำ:** รัน `ffmpeg silencedetect` หาทุกจุดเงียบ (noise=‑35dB, d=0.3) แล้วเก็บเฉพาะ **ช่วงต้น** ของความเงียบเดิมมาแทนความเงียบทั้งก้อน (ไม่ใช้ความเงียบดิจิทัลล้วน จะได้รูมโทนธรรมชาติ ไม่รู้สึกตัดแปะ) — cap ตามกฎเดียวกับ TTS breaks ด้านบน: ช่วงหยุดสั้น (<1s) เหลือ 0.25s, ช่วงหยุดยาว/รอยต่อประโยค (≥1s) เหลือ 0.55s, ช่วงเงียบนำหน้าไฟล์ (ก่อนคำแรก) เหลือ 0.10s เท่านั้น

**เชนที่ใช้จริงและผ่าน** (หลังหดช่วงเงียบแล้ว):
```
highpass=f=70, afftdn=nf=-40,
acompressor=threshold=-24dB:ratio=2.3:attack=15:release=220:makeup=2,
equalizer=f=3000:t=q:w=1.2:g=1.5, equalizer=f=9000:t=q:w=1:g=1.5,
loudnorm=I=-20:TP=-1.5:LRA=6 (two-pass, linear=true),
alimiter=limit=0.891:level=disabled
```
ผลลัพธ์จริง: ต้นทาง ‑31.1 LUFS / 150.1s / 13.2MB → ปลายทาง ‑20.04 LUFS / true peak ‑1.5dBTP / 0 clipped / **1:56.2 / 9.77MB** (โจทย์: ไม่เกิน 2 นาที ไม่เกิน 10MB)

**ทำไมต้องคุมขนาดไฟล์แบบนี้:** WAV 16-bit 44.1kHz mono กินพื้นที่ตรงตัว ~88,200 ไบต์/วินาที เพดาน 10MB จึงเทียบเท่า **~118.9 วินาทีเป๊ะ** — ต้องเผื่อ margin ให้เหลือ ~115s ไม่ใช่กะตัดที่ 120s พอดี เพราะจะดันไฟล์ทะลุ 10MB

**วันที่:** 2026-08-08

## บทเรียน: TTS บางรอบอ่านเร็วกว่าเกณฑ์มาตรฐาน (12.3 ตัวอักษร/วิ) จนความยาวตึงกับกฎ mid-roll — แก้ด้วยการปรับ cap ตัดเงียบ ไม่ใช่เขียนบทเพิ่ม

คลิป 009 พบว่า ElevenLabs อ่านเร็วถึง 13.03 ตัวอักษร/วินาที (เร็วกว่าเกณฑ์ ~6%) ทั้งที่บทยาวใกล้เคียงคลิปก่อนหน้ามาก — ตัดช่วงเงียบด้วย cap มาตรฐาน (CAP_NORMAL=0.35s) แล้วได้ความยาวรวม (รวม end credit) เกิน 8 นาทีแค่ 0.21 วินาที ตึงเกินไป

**ทางแก้ที่ใช้ได้ผล:** เพิ่ม `CAP_NORMAL` จาก 0.35s เป็น 0.42s (คง `CAP_LONG`=0.90s ที่ใช้กับรอยต่อบทจริงไว้เท่าเดิม ไม่แตะ) — ได้ margin ความยาวกลับมาอีกหลายวินาทีโดยไม่กระทบคุณภาพเสียง/LUFS/LRA เลย วิธีนี้ปลอดภัยกว่าการเขียนบทเพิ่มหรือยืดปลายคลิปเทียมทีหลัง — **ความเร็วการอ่านของ ElevenLabs ไม่คงที่ข้ามการ generate แม้ใช้เสียง/การตั้งค่าเดียวกัน** ต้องเช็คความยาวไฟล์ดิบจริงเทียบเกณฑ์ 12.3 ตัวอักษร/วิทุกครั้ง ไม่ใช่เชื่อว่าจะแม่นเป๊ะเสมอ ถ้าความยาวตึงให้ปรับ `CAP_NORMAL` ขึ้นเป็น 0.40–0.45s ก่อนพิจารณาทางอื่น

## บทเรียนใหม่: ElevenLabs อาจเติมคำพูดที่ไม่มีในบทต่อท้ายไฟล์เสียงเอง — ต้องตรวจ SRT ท้ายไฟล์เทียบกับบทจริงเสมอ

คลิป 007 (fingerprint) — ตอนอ่าน SRT ที่ได้จาก SayToWords (`ElevenLabs_007_mastered.srt`) เพื่อเตรียมสร้าง Timecode Map พบว่า **segment สุดท้าย (177) มีข้อความ "สวัสดีครับ" ที่ไม่มีอยู่ในบทต้นฉบับเลย** ต่อท้ายประโยคจริงสุดท้าย ("...มาตลอดทั้งชีวิต") พอดี ที่เวลา 08:37.942–08:38.245 (0.303 วินาที)

**ยืนยันว่าเป็นเสียงพูดจริง ไม่ใช่แค่ SRT หลอน:** วัดค่า RMS ของคลื่นเสียงช่วงนั้นด้วย python (`wave`+`numpy`) พบพลังงานเสียงจริงสูง (RMS 6,000–9,000) ไม่ใช่ความเงียบ — เป็นคำพูดจริงที่ ElevenLabs สร้างเติมเข้ามาเอง (known issue ของ TTS บางรุ่นที่เผลอเติมคำทักทาย/ปิดท้ายแบบสุ่มตอนจบการ generate แบบยาว)

**วิธีแก้:** ตัดไฟล์เสียงมาสเตอร์ที่ตำแหน่ง 517.942 วินาที (จุดที่ SRT บอกว่า "สวัสดีครับ" เริ่ม — เชื่อค่าที่ ASR วัดมาเพราะแม่นกว่าการหาขอบเสียงด้วยตาจาก RMS เนื่องจากเสียงพูดสองท่อนต่อกันแนบสนิทไม่มีช่วงเงียบจริงคั่น) ใส่ fade-out สั้น 0.05 วินาทีกันเสียงป๊อก ยืนยันซ้ำว่า loudness/peak/clipped ไม่เปลี่ยนหลังตัด (I -14.6 LUFS, LRA 2.1, TP -1.2 dBFS, clipped 0 เท่าเดิม) แล้วใช้ไฟล์ที่ตัดแล้วเป็นไฟล์ทางการต่อ (เก็บไฟล์เดิมไว้เป็น `.wav.bak_hadstray` ไม่ลบทิ้ง)

**กฎใหม่จากนี้ไป:** ก่อนเริ่มสร้าง Timecode Map ทุกครั้ง **ต้องอ่าน SRT ทั้งไฟล์เทียบกับบทต้นฉบับคร่าว ๆ ก่อนเสมอ โดยเฉพาะ segment แรกและ segment สุดท้าย** เพื่อจับกรณี TTS เติมคำที่ไม่มีในบท (ไม่ใช่แค่ปัญหา ASR สะกดผิดแบบที่เจอทั่วไป) — ถ้าเจอคำแปลกที่ไม่มีในบทเลยแม้แต่คำเดียว ให้ตรวจสอบด้วย RMS ว่าเป็นเสียงพูดจริงหรือไม่ ถ้าใช่ให้ตัดไฟล์เสียงออกที่ตำแหน่ง SRT บอกไว้ก่อนเริ่มขั้นตอน anchor matching เสมอ ไม่งั้นความยาวไฟล์เสียงจะไม่ตรงกับความยาวบทจริง ทำให้ผลการคำนวณ Timecode Map ทั้งหมดคลาดเคลื่อน
